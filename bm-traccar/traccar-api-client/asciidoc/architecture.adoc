== Architectural Design

- **Separation of Concerns** +
  The architecture separates generated API code in `traccar-openapitools-client` + 
  from business logic via `Api interface` in  `traccar-api-client`.
  
- **Generated API Layer** +
  All REST API models and client classes are generated from the Traccar OpenAPI spec (`yaml`) +
  and maintained in `traccar-openapitools-client`.
  
- **Extensible Client** +
  `traccar-api-client` wraps and extends the generated API, + 
  providing a stable interface for application developers.

== Traccar API @Service

The Traccar OpenAPI Client wraps the Traccar API in a Spring @Service -- simple as that. +
You can always counter check against the latest 
link:https://www.traccar.org/api-reference[Official Traccar API Reference].

=== usage

After adding the jar to your software or build system 
the API can easily be added to any Springboot Application as a @Service in your code

      @Autowired private ApiService api;

=== authentication

Then you can set your credentials via bearer token or basic authentication

    // use your token generated from your Traccar server
    api.setBearerToken(YOUR_TRACCAR_TOKEN);
    // switch auth method
    api.setBasicAuth(mail, password);
    // switch for every REST call as needed

or switch users with different access to different user, devices etc.
directly in your code. +
see `package bm.traccar.invoke.auth`


=== usage example

Here's a simple example code to demo how to add the Traccar API Service 
to your company software. +
First you need these prerequesites: 

* Add the `traccar-api-client-x.y.z.jar` to your application. +
Or add it to your `.m2` repo or nexus server, then to _your_ `pom`.

* Add your Traccar Server URL and credentials to your `application.properties` file. +
i.e. `host, user.name, user.password, user.email (, accountToken)`. +
Or provide these values in a way that meets your security strategy (secrets etc.)

and then the coding is straight forward:

[source,java]
----
package your.company.app...;

import bm.traccar.api.ApiService            // <1>

public class TraccarUsers {

    @Autowired
    private ApiService api;                 // <1>

    public static void main(String[] args) { 
    
        api.setBasicAuth(mail, password);   // <2>
//      api.setBearerToken(token);
        
        User user = new User();             // <3>
        user.setName("user-1");
        user.setEmail("email-1");
        user.setPassword("pw-1");
        
        User userOnServer = api.getUsersApi().createUser(user);     // <4>
        
    }
}
----
<1> add the `ApiService`, being a Spring `@Service class`

<2> choose and set your authentication +
and can change it any time in the program flow.

<3> create a `new User` (DTO) in your software for your employees 

<4> create a `new User` (Entity) in your Traccar Server +
The new User (DTO) is returned with a unique ID from the server.  

=== mimic URL syntax

You can always check your authentication by calling a REST endpoint in your browser

  http://localhost/api/users/257          works in service account
  http://localhost/api/users?userId=256   doesnt

Note how the Java invokation mimics a REST call

    // <server>/api/users?user_Id=11
    User user = api.getUsersApi().getUsers(userId);

And that is all you need to create users, devices etc.
and manage them in your code! +
For more examples check the integration tests, i.e. `UsersIT` and others.

As you can see the above expression is similar the URL

    http://{host}:{port}/api/users/{id}
    User userOUT =       api.getUsersApi().createUser(user);

    https://localhost/api/devices?id=3
    Device[] devices =   api.getDevicesApi().getById(3);

For convenience you can use the `application.properties` file 
and grab the `@Value` in your source code, depending on your security concepts.

For integration testing with docker we apply a fixed `serviceAccountToken`

== Traccar API Identity Model

The `traccar-api-client` is designed for a **single User identity at a time**.

=== Single-Identity Design

Authentication state in `traccar-api-client` is maintained as global mutable state on the shared singleton `ApiClient` instance:

- **Global Scope**: Calling `api.setBasicAuth(...)` or `api.setBearerToken(...)` mutates credentials globally on the underlying singleton `ApiClient`. This affects every caller in the JVM executing subsequent requests, including background tasks and WebSocket routes relying on those credentials.
- **One `Api` Bean == One Identity**: At any given moment, the injected `Api` bean represents a single authenticated identity. It is **not thread-safe across concurrent identities**.
- **Multi-Tenant / Concurrent Identities**: If multi-tenant usage or concurrent operations under different identities are required in the future, a per-identity client factory (or thread-local / request-scoped client instances) must be introduced instead of mutating the shared singleton.

[IMPORTANT]
====
In a multi-threaded application, do not switch authentication (`setBasicAuth` / `setBearerToken`) concurrently across different threads sharing the same `Api` bean.
====


== Traccar API Interface

The `ApiService` is the Spring implementation of the `bm.traccar.api.Api` interface.
Application code should depend on the *interface*, not on the service class,
so the implementation can be swapped (or mocked) without touching your code.
The sub-APIs are accessed exclusively via the `get<SubApi>Api()` getters
which mirror the Traccar REST tags:

[cols="1,2,2"]
|===
| REST tag | getter | sub-API

| `/server`      | `api.getServerApi()`      | `Api.Server`
| `/session`     | `api.getSessionApi()`     | `Api.Session`
| `/users`       | `api.getUsersApi()`       | `Api.Users`
| `/devices`     | `api.getDevicesApi()`     | `Api.Devices`
| `/permissions` | `api.getPermissionsApi()` | `Api.Permissions`
|===


=== Example: Create a User

Here is a simple example code to demo how to add the Traccar API Service 
and create a new user on your Traccar Server with the `UserApi`. 

[source,java]
----
package your.company.app...;

import bm.traccar.api.Api                   // <1>

public class TraccarUsers {

    @Autowired
    private Api api;                        // <1>

    public static void main(String[] args) { 
    
        api.setBasicAuth(mail, password);   // <2>
//      api.setBearerToken(token);
        
        User user = new User();             // <3>
        user.setName("user-1");
        user.setEmail("email-1");
        user.setPassword("pw-1");

        User userOnServer = api.getUsersApi().createUser(user);   // <4>
    }
}
----
<1> auto wire the `Api` interface (the `ApiService` bean is injected)

<2> choose and set your authentication 

<3> create a `new User` (DTO) in your software for your employees 

<4> create a `new User` (Entity) on your Traccar Server via the Users sub-API

You can also hold on to an individual sub-API:

    Api.Users users = api.getUsersApi();
    User newUser = users.createUser(user);

This is convenient if you don't want to mess with many APIs
and focus the implementation on User Management, for example.


=== summary

The `Api` interface is the sole public contract. +
It declares one `get<SubApi>Api()` per Traccar REST tag; +
`ApiService` receives the `Api.*` sub-API components via constructor injection. 

The *core idea* is a single `Api` interface with nested sub-API interfaces (`Api.Users`, ...), + 
each `*Impl` is a `@Component` wrapping its generated `*Api` bean, +
the `@Service` `ApiService` aggregates them, +
and AOP translates all `RestClientException` -> `ApiException`. +
That is a clean anti-corruption layer over generated code.

Each `*Impl` is a `@Component` with its own constructor injection (`UsersImpl(UsersApi)`) +
and have `ApiService` inject the `Api.Users, Api.Devices`, …​ beans. + 
This keeps the constructor manageable and allows consumers to optionally inject `Api.Users` directly.

As the core rule: "a generated *Api must be a Spring bean or the aspect will not fire". +
Check _Traccar ApiAspect_ section for details.
