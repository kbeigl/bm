== API Implementation

This software is based on a generated *Java Spring REST Client* from the Traccar REST specification.
The single package (`bm.traccar.api`) implementation wraps the Java client in a *Spring* @Service
to be applied wherever feasible. The API client completely hides the REST intricities
inside regular Java methods.

The `traccar-api-client` is basically a single package application or rather _service_. +
In addition there is a websocket package to receive live information from the Tracking System.


[TIP]
====
If you are looking for the usage of the Traccar API and sub APIs +
you can go directly to the 
xref:./api/sub-api-implementations.adoc[Traccar API page].
====

== Traccar REST

Traccar `v6.7` provides *17 APIs* (see `package bm.traccar.generated.api`)
and as the GTS progresses + 
Traccar `v6.12.2` provides *19 APIs*.
These APIs support many aspects of GPS Tracking and beyond, like health monitoring.

The `traccar-api-client` defines _one single (nested) API interface:_ 
`bm.traccar.api.Api`, which allows us to switch the implementation.
This was required, for example, when changing from swagger to OpenAPI (3 to 3.1). +

[TIP]
====
Therefor you should stick to the `bm.traccar.api.Api interface` 
to connect your program logic!
====


=== Data Transfer Objects - DTOs ...

In addition the `traccar-api-client-6.7` provides *21 Data Transfer Objects* +
and `v6.12.2` already has 26 (package `bm.traccar.generated.model.dto`).

These DTO _represent_ the different System Entities 
and are used to exchange information with the server. +
For example the User API call to 
link:https://www.traccar.org/api-reference/#tag/Users/paths/~1users/post[Create a User] 
is provided as Java method by the Api interface:

[source,java]
----
    public interface Api {
           interface Users {
                User createUser(User user) throws ApiException;
----

In your code you can easily create a `new User()` in your software 

[source,java]
----
    User userIN = new User();
    userIN.setName(usr);
    userIN.setEmail(mail);
    userIN.setPassword(pwd);
    userIN. ...
----
    
and  then create it on server side and receive a copy:

[source,java]
----
    User userOUT =  api.getUsersApi().createUser(userIN);
----

Note that `userIN` and `userOUT` are different instances,
i.e. `userIN` on client and `userOUT` is returned from server.
The latter provides the `userId` provided by the Traccar Model
and is vital to use in the client server communication.
The ID is usually hidden for external users (i.e. in the UI),
but required for unambiguously user identification!


=== ... are not System Entities

Nevertheless you should always distinguish _Data Transfer Objects_
from actual Entities in the Systems _Entity Relations Model_ - ERM.
_The Traccar System_ is build around the _Traccar Data Model_,
which is represented in the 
link:https://github.com/traccar/traccar/tree/master/src/main/java/org/traccar/model[model package],
while the DTOs are created in the
link:https://github.com/traccar/traccar/tree/master/src/main/java/org/traccar/api/resource[resource package].
The Entities are only accessed by Traccar itself, while DTOs are snapshots of them.
The Traccar Database is the best place to monitor what's going on.

This is similar to DNA and RNA: +
The DNA (ERM) is part of the _living_ organic System, +
while the RNA (DTOs) is simply a copy of the DNA from a certain point in time.


== Traccar `ApiAspect`

This API client implementation applies _Aspect-Oriented Programming_ (*AOP*) 
as the technique for handling exceptions in Spring Boot applications. 
This way all exception handling happens in one central `ApiAspect` class 
and avoids code duplication.

We apply AOP, since the Traccar REST API is a moving target.
SubAPIs are added, methods and types are changed etc.
With AOP we can grasp a general pattern that applies to _all_ sub APIs,
even the ones we haven't implemented or Traccar will offer in future.

Generally any problem in the client software should through an `ApiException` 
to take over responsibility and to provide useful messages for developers 
and wrap the cause for deeper analysis.

[IMPORTANT]
====
The `ApiAspect` is registered by `ApiConfig` (`@Import(ApiAspect.class)`).
Importing `ApiConfig` is therefore the complete contract for consumers:
you get the generated `Api` beans *and* the `ApiException` translation --
no component scan of `bm.traccar.api` is required.

The generated `*Api` instances must be Spring beans (as declared in `ApiConfig`),
otherwise Spring AOP cannot proxy them and no `ApiException` is thrown.
This contract is verified without a Traccar server by `ApiConfigAspectTest`.
====

As you can see in the `bm.traccar.api.ApiAspect` class 
the `@Around` advice covers all `*Api` classes in the generated package:

      @Around("within(bm.traccar.generated.api.*Api)")

Any `Throwable` raised inside is wrapped in an `ApiException` with a helpful message;
`RestClientException` subtypes (no connection, 4xx, 5xx) are mapped to the
`ApiException.APIEX_*` message constants.

Note that the `ApiException` is a `RuntimeException` and 
the caller is not forced by the compiler to catch it.
However you should handle it as good practice
and to ensure that you have a binding communication.

[source,java]
-----------------
    Spring AOP
    invocation order
        invoke **UsersApi.usersPost(..) ** <-------------+
          invoke ApiClient.selectHeaderAccept(..)        |
          invoke ApiClient.selectHeaderContentType(..)   |
          invoke ApiClient.invokeAPI(..)                 |
        Exception in ApiMethod: **UsersApi.usersPost(..) **
-----------------


== Traccar `ApiException`

The `bm.traccar.api.ApiException` is the central unchecked exception class 
used throughout the API client. Every raw HTTP error, connection timeout, authentication failure, 
or unexpected REST exception caught by `ApiAspect` is converted into an `ApiException`.

As a `RuntimeException`, callers are not required by the compiler to catch it with boilerplate code, 
yet it provides rich structured details for programmatic recovery and diagnostics.


=== Properties and Structure

Each `ApiException` carries:

* **`errorCode`** (`ApiErrorCode`): A typed enum value representing the category of failure.
* **`statusCode`** (`Integer`): The HTTP status code returned by the server (e.g. `400`, `401`, `404`, `500`), or `null` if the error occurred prior to receiving a response (such as connection timeouts).
* **`message`** (`String`): A developer-friendly description of the error.
* **`cause`** (`Throwable`): The wrapped underlying exception (such as `ResourceAccessException` or `HttpStatusCodeException`) for root-cause inspection.


=== Error Constants 

`ApiException` provides standardized message constants `APIEX_*` for common error scenarios:

[cols="1m,2,2", options="header"]
|===
| Constant | Value | Description

| APIEX_NO_CONNECTION
| `"Cannot connect to server!"`
| Network or transport failure; indicates that the Traccar server could not be reached.

| APIEX_UNAUTHORIZED
| `"Unauthorized: check credentials!"`
| Authentication or authorization failure (HTTP 401 Unauthorized or 403 Forbidden).

| APIEX_BAD_REQUEST
| `"Request returned error!"`
| Invalid request payload, constraint violation, or duplicate primary key (HTTP 400 Bad Request).

| APIEX_CLIENT_REST
| `"Exception with REST client!"`
| General client-side REST communication or response processing exception.
|===


=== `ApiErrorCode` Enum

To allow type-safe programmatic handling (e.g. initiating server reconnection loops vs. requesting new user credentials), 
the `ApiErrorCode` enum categorizes the failure:

[cols="1m,1m,3", options="header"]
|===
| ApiErrorCode | HTTP Status | Description

| NO_CONNECTION
| null
| Transport/network error (connection refused, host unreachable, connection timeout). Used to trigger reconnect intervals.

| UNAUTHORIZED
| 401 / 403
| Authentication or permission failure. Token expired or invalid credentials.

| BAD_REQUEST
| 400
| Request validation failure, missing mandatory attributes, or constraint violations.

| NOT_FOUND
| 404
| The requested resource or endpoint does not exist on the server.

| CLIENT_REST
| varies
| Generic REST communication error, unparseable payload, or unknown content type.

| SERVER_ERROR
| 5xx
| Server-side internal error occurred in the Traccar backend.

| UNKNOWN
| null
| Unclassified or unexpected runtime exception.
|===


=== Exception Mapping in `ApiAspect`

The central `ApiAspect.createApiException(Throwable)` method evaluates intercepted exceptions +
and maps them to typed `ApiException` instances:

[cols="2m,1m,1m,2", options="header"]
|===
| Intercepted Exception | ApiErrorCode | Status Code | Error Message

| ResourceAccessException
| NO_CONNECTION
| null
| `ApiException.APIEX_NO_CONNECTION`

| HttpStatusCodeException (400)
| BAD_REQUEST
| 400
| `ApiException.APIEX_BAD_REQUEST`

| HttpStatusCodeException (401, 403)
| UNAUTHORIZED
| 401 / 403
| `ApiException.APIEX_UNAUTHORIZED`

| HttpStatusCodeException (404)
| NOT_FOUND
| 404
| Original exception message

| HttpStatusCodeException (5xx)
| SERVER_ERROR
| 5xx
| `"Server error: " + sc`

| HttpStatusCodeException (other 4xx)
| CLIENT_REST
| 4xx
| Original exception message

| UnknownContentTypeException
| CLIENT_REST
| Status code
| Original exception message

| RestClientResponseException
| CLIENT_REST
| Status code
| `ApiException.APIEX_CLIENT_REST`

| RestClientException
| CLIENT_REST
| null
| Original exception message

| Other Throwable
| UNKNOWN
| null
| `"An unexpected error occurred: " + thrown.getClass().getName()`
|===


=== Handling `ApiException` 

Client applications can inspect the typed `errorCode` or `statusCode` to decide on appropriate recovery strategies:

[source,java]
----
	try {
	    User createdUser = api.getUsersApi().createUser(user);
	    logger.info("User created with ID: {}", createdUser.getId());
	} catch (ApiException ex) {
	    switch (ex.getErrorCode()) {
	        case NO_CONNECTION -> {
	            logger.warn("Traccar server is unreachable. Scheduling reconnect interval...");
	            reconnectService.scheduleRetry();
	        }
	        case UNAUTHORIZED -> {
	            logger.error("Authentication failed: check bearer token / credentials.");
	            authService.refreshToken();
	        }
	        case BAD_REQUEST -> {
	            logger.error("Bad request (status {}): {}. 
	                          Check input parameters or duplicates.",
	            ex.getStatusCode(), ex.getMessage());
	        }
	        case NOT_FOUND -> {
	            logger.warn("Resource not found: {}", ex.getMessage());
	        }
	        case SERVER_ERROR -> {
	            logger.error("Traccar server error (status {}): {}", 
	            ex.getStatusCode(), ex.getMessage());
	        }
	        default -> {
	            logger.error("API error [{}]: {}", ex.getErrorCode(), 
	            ex.getMessage(), ex.getCause());
	        }
	    }
	}
----
