== Real Time Implementation

We will look at Real Time Systems in general and 
derive some requirements for a Real Time Client for Traccar Server.
We will discuss the design of the `RealTimeManager` and `RealTimeController`,
which are the core components of the `traccar-realtime-client` and
provide a thread-safe state management for the Traccar Model of Entities and Relations.



== Real Time Systems

Modern Advanced Driver Assistant Systems (ADAS) can serve as an example of a _Real Time System_.
They are monitoring the vehicle _and_ observing the environment 
every instance of the motion. With a 5 GHz network the computational power can take place
in large server farms, while the vehicle basically provides events and values from detectors.

[IMPORTANT]
====
The term _real time_ refers to the actual computational results provided _as the incident takes place_. +
Therefor Real Time Systems are systems that can actually interfere the incident in reality.
====

Today ADAS have become Self Driving Systems and can actually drive a car 
and predict the trajectory by reading the road map.

[quote, see https://en.wikipedia.org/wiki/Real-time_computing]
____
A real-time system has been described as one which "controls an environment by receiving data, 
processing them, and returning the results sufficiently quickly to affect the environment at that time".

A system not specified as operating in real time cannot usually guarantee a response within any timeframe, 
although typical or expected response times may be given. 
Real-time processing fails if not completed within a specified deadline relative to an event; 
deadlines must always be met, regardless of system load. 
____


GPS Tracking usually implies _live tracking_ and allows us to locate something on a map.
Of course _live_ is relativ and we have to rely on connectivity and accept a little latency.
For example vehicles can not be GPS tracked in most tunnels due to missing satelite information.
A Real Time Client could detect this and make a prediction, 
 when the vehicle will exit the tunnel and be _GPS fixed_ again.


=== Real Timing

Structuring the data for a real-time application like a Traccar Client is crucial for performance and maintainability. +
As a development guideline we do not want to use any back doors to Traccar, like a direct database access.
We treat Traccar as a mature component with endless configuration options and 
we want to communicate the official way (front door), i.e. over Traccar REST API via `traccar-api-client`.

Traccar is taking care of the connectivity to all (tens of thousands of different) GPS Trackers,
stores there info, raises events, while we only need the one connection to the Traccar Server
to interact via REST API and retrieve real time data via Websocket.
Even, if we would design real-time code directly to the Traccar Database 
this does not guarantee to be much faster. 
And there's a risk to interfere with the Traccar Controllers and run into integration issues.

We could use an in-memory-database like h2, which is also supported in Spring Boot and Maven.
Yet this would have the draw back to create objects during the real time calculation.
We will create a *Real Time Manager* that has all objects in place and state changes occur immediately
only restricted by the CPU speed.

Its a race between real time client connectivity / loading against persisting on server side.
If you place the `traccar-realtime-client` in the same environment as your Traccar server
there are chances that the client is triggered before the database update has finished.
Nevertheless the objects are related over _Traccar Database IDs_, which are indispensable.

=== when and where

Another important aspect about 'real time development' is the usage of the provided timestamps
in chronological order: `fixTime`, `deviceTime` and `serverTime`. 
The _GPS Fixtime_ describes, when the Position was calculated and fixed. 
This fixtime is calculated by the _GPS Unit hardware and chip_ in the field
with the most precise atomic clocks available.
The calculation is relativistic and aware of the satelites positions and much more.
The fix is usually made when the parameters provide a result with best accuracy
and this can differ due to the environmental conditions.

[IMPORTANT]
====
Real Time Developers should stick to the `fixTime` in order + 
to get the actual universal time *when and where* + 
the fix (or event) has occured -- *in reality*.
====

The `deviceTime` is the point in time when the position and event are sent. +
Consecutive messages _can_ have the same `fixTime`. +
The `serverTime` is the time, when the position and event are persisted. +
It can provide clues about the connectivity and network latency.


== Real Time Data Structures

Traccar manages its Entities and Relations with an Entity Relational Data Model - ERM.
So we need to define a robust data structure to work with Entities and Relations 
in the RAM, i.e. Software.

Core Design Principles

* Centralized State + 
    All data is held in a single, well-defined state object. 

* Normalization +
    Each entity type (`User, Device, Position, Geofence`..) is stored in its own "table" or `map`. +
    Objects reference each other by `ID` rather than nesting the full object. 
    This prevents data duplication and makes updates atomic. 
    For example, a `Device` object will contain a `positionId` instead of the entire position object.

* Maps for _fast_ `O(1)` Lookups +
    Data is stored in Maps where the key is the entity's `id`. +
    This allows for extremely fast lookups when an update comes in, 
    which is essential for real-time performance.
    

== RealTimeManager

The `RealTimeManager` is a thread-safe Singleton class 
to manage the concurrent real-time state of the Traccar client, 
also known as StateManager in RealTime context.
A dual-lock approach (`ConcurrentHashMap` for concurrent _reads_ 
and `synchronized (deviceMapLock)` for multi-map atomic _writes_) 
always assures a stable realtime state.

    •  It is annotated with `@Component`, so Spring creates a singleton for the application context.
    •  It uses `ConcurrentHashMap` for its internal state, 
       which provides thread-safe access +
       and updates from WebSocket listener background threads.

[source,java]
----
  private final Map<Long, User>     users     = new ConcurrentHashMap<>();
  private final Map<Long, Device>   devices   = new ConcurrentHashMap<>();
  private final Map<Long, Position> positions = new ConcurrentHashMap<>();
----

•  Synchronization is used (`deviceMapLock`) to ensure atomic updates for related maps.
•  The class manages real-time entities (`User, Device, Position ..`) + 
       and their relationships safely across threads.

Note that there is no API involved.


=== RealTimeManagerIT

Data Flow & Interaction

Next we need to develop methods for state modifications. +
We have to load initial entities and then update them 
from the live data coming in over a websocket connection.

Basically we will use the `RealTimeManager` in these sequentiell steps:

1. _Authenticate_ on Traccar Server and receive a `User` object with a database ID. +
Store `User` in  `RealTimeManager` with `setLoginUser(User user)`.

2. _Load_ initial data for the scenario by fetching the entities from Traccar 
and converting them to a Map. +
Optionally collect last known `Position` objects for the `Devices`.

3. _Connect_ to websocket and receive live data. +
Traccar pushes JSON object arrays to be transformed 
and then updated on individual entities.

Have a look at these `RealTimeManagerIT` snippets to identify the steps listed above
as you read on:

=== add or update

The `addOrUpdatePosition` method shows how the `RealTimeManager` works.
It is called when a new position update is received, either from the WebSocket or any other
source. 
The method checks if the position already exists in the `positions` map. 
If it does, it _updates the existing position instance_; if not, it adds a new entry.
                    
This `addOrUpdate<Entity>` approach ensures that we maintain a consistent state in the `RealTimeManager`
while allowing for efficient updates without needing to replace entire objects in the map.
                    
Another vital aspect of programming are object _references_!

When receiving a new Device update, we could simply replace the whole `Device` object in the `devices` map.
However, this would _break the Java reference_ to the `Device` by the users of the `RealTimeManager`. 
Copy-on-write (create a new merged Device and atomically replace it in the map) ensures 
that _all references remain_ valid and consistent across the application.
Updating fields in-place _preserves references_, but requires explicit 
synchronization or thread-safe fields to avoid races and visibility problems.

We are using Spring's `BeanUtils` to copy the properties from the new Device to the existing one in the map.

[source,java]
----
        // copy properties to preserve object references for external holders
        BeanUtils.copyProperties(device, previous);
----

== RealTimeController

Now that we can safely read from the `RealTimeManager` we will create a `RealTimeController` for synchronization. +
The `RealTimeManagerIT` test is holding the `private RealTimeManager` in order to test it's methods. +
The `RealTimeController` owns Api, WebSocketRoute and the state Manager 
and is a Spring Component that encapsulates the logic for interacting with the Traccar server. 

The `RealTimeController` is the subsequent implementation keeping the `RealTimeManager` private
to control it's state by synchronizing the server updates.
The Controller encapsulates all the logic in communicating with the Traccar server.
It handles authentication, fetches the initial state via the REST API, 
and then connects to the WebSocket to receive and process live updates, 
feeding everything into the thread-safe state manager.

Basic `RealTimeController` design becomes apparant in the constructur: 

[source,java]
----
	@Component                                            // Spring creates a singleton
	public class RealTimeController {
	
	  private final RealTimeManager stateManager;         // exclusive to controller
	  private final Api api;                              // active server access
	  private final WebSocketRoute liveConnection;        // background server updates
	
	  public RealTimeController(RealTimeManager stateManager, // injected by Spring
                      Api api, WebSocketRoute liveConnection) {
	    :
----

We will look at the `WebSocketRoute` soon. +
For now you can run the `RealTimeClientIT` (or `LoadRealTimeClientIT`) 
which basically executes the line

[source,java]
----
  controller.loginAndInitialize(scenario.admin)
----

for authentication, loading of initial server Entities 
and establishing a live connection via WebSocket.

== Database IDs

If you are familiar with the Traccar frontend you will not find any database IDs in the GUI. +
This is also desireable for a Real Time Client, because the database IDs are purely technical. +
If you are using a Test database and run the same test twice, the database IDs will differ. 

Nevertheless the database IDs are indispensable *inside* the software stack +
and we have to be clear about _where_ they are used and _where_ they are hidden.

=== internal IDs
 
// === IDs in `traccar-api-client` and `RealTimeManager`

The `traccar-api-client` is a one-to-one representation of the Traccar REST API
and therefore works with database IDs throughout:
`getDevice(id)`, `updateUser(id, user)`, `deleteDevice(id)` and so on. +
Traccar's model is an ERM and the entities reference each other by ID, 
exactly as described in the xref:_real_time_data_structures[core design principles] above.

The `RealTimeManager` mirrors this model in memory. +
Its maps are keyed by database ID and the relations are kept as IDs:

[source,java]
----
  private final Map<Long, User>     users     = ..;   // key = user.id
  private final Map<Long, Device>   devices   = ..;   // key = device.id
  private final Map<Long, Position> positions = ..;   // key = position.id
  // natural key -> technical key
  private final Map<String, Long>   deviceIdByUniqueId = ..;
----

This is the only way to apply a live update consistently:
a `position` message carries a `deviceId`, the Manager looks up the `Device` 
by that ID in `O(1)` and sets `device.positionId`.
Without the IDs the Manager could not resolve the relations at all.

=== hidden IDs

// === IDs hidden by the `RealTimeController`

The `RealTimeController` is the boundary to the client user application. +
Its job is to hide the technical IDs and to offer the entities by their _natural keys_:

[cols="1,1,2", options="header"]
|===
| Entity   | natural key   | Controller method

| `Device`   | `uniqueId` (IMEI or similar)  | `getDeviceByUniqueId(String uniqueId)`
| `Position` | the device it belongs to      | `getLatestPositionForDevice(String uniqueId)`
| `User`     | `email` (login name)          | `getUserByEmail(String email)`
|===

[IMPORTANT]
====
Application code addresses entities in a *natural way* -- by `uniqueId` and `email` -- 
and never passes a database ID *into* the Controller. +
The Controller resolves `uniqueId → deviceId → positionId` internally via the Manager.
====

The returned DTOs (`Device`, `Position`, `User`) are the generated API model classes
and still carry their IDs (`device.getId()`, `position.getDeviceId()`, `device.getPositionId()`).
This is intended: the IDs are needed to understand the relations -- 
but they are _read-only information_ for the application, not an address.
Methods like `getUserById(long)` or `getLatestPositionForDevice(long deviceId)`
are deprecated on the Controller for exactly that reason.


=== example

The uniqueId is the hinge between the physical world and the database. +
A `TrackerOsmAnd` sends messages with its `uniqueId=10`,
the Traccar Server resolves it to the device with the database `id=554`
and persists a position with `deviceId=554`:

    {devices=   [{id=554, uniqueId=10,  positionId=198, ...}]}
    {positions= [{id=198, deviceId=554,                 ...}]}  // deviceId is NOT the uniqueId!

The application only knows the `uniqueId=10` from its scenario and asks the Controller:

[source,java]
----
  // tracker and controller share the uniqueId - no database IDs involved
  String uniqueId = runnerTracker.getUniqueId();                                  // "10"
  Optional<Device>   device = controller.getDeviceByUniqueId(uniqueId);           // id=554
  Optional<Position> latest = controller.getLatestPositionForDevice(uniqueId);    // id=198
----

If the scenario is loaded into a fresh database the IDs will be `id=1234` and `id=42`,
but the application code does not change -- it is addressed by `uniqueId=10` as before.
This actually happens with every Integration Test run.

[IMPORTANT]
====
A user of the `RealTimeController` should be aware that tracker, player and device +
are all the same Entity and share the same `uniqueId`. This should be intuitive. 
====

== conclusion

This Java structure provides a clean, scalable, and safe way to manage your Traccar client's data. + 
The `RealTimeController` calls `setLoginUser` and `loadInitialDevices` on the `RealTimeManager` 
after authenticating via the REST API, +
while the WebSocket processors call `addOrUpdatePosition` and/or other Entities through the Controller. + 
The `traccar-api-client` and the `RealTimeManager` work with database IDs to keep the relations intact, +
the `RealTimeController` hides them and lets the application 
address entities by `uniqueId` and `email`.
