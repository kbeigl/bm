=== Running the Realtime Application

The `traccar-realtime-service` comes with a `RealTimeApp` class 
that _can be used_ to run the Realtime Service as a standalone Spring Boot application. 
If you have your own Realtime Application, you can use the `RealTimeRunner` class 
to run your application as a Spring Boot application.

As a quickstart, you can place the `jar` file in any directory and +
run the `traccar-realtime-service` as a standalone application using the following command:

	$/bm/bm-traccar/traccar-realtime-service$ 
		java -jar target/traccar-realtime-service-6.14.2-1.1.28-exec.jar 

or as long as you are inside the repository, you can run it using Maven:
	
	$/bm/bm-traccar/traccar-realtime-service$ mvn spring-boot:run

The service will start and attempt to login to the Traccar server 
using the default credentials of the `application.properties` file. 

Make sure the credentials are correct and the Traccar server is running before starting the Realtime Service.

If the login is successful, you will see a message indicating that the Realtime Service has started successfully.

 RealTimeApp        - Starting RealTimeApp using Java 25.0.4.1 with PID 662128 
 RealTimeApp        - Started RealTimeApp in 3.704 seconds (process running for 4.369)
 RealTimeRunner     - Login RealTimeController 
                      for 'admin@scenario.com' to traccar server 'http://localhost:80` ...
 RealTimeController - --- Loading initial users from server...   ---
 RealTimeController - --- Loading initial devices from server... ---
 RealTimeController - User logged in: admin
 RealTimeRunner     - RealTimeController started and logged in successfully.
 RealTimeRunner     - RealTimeService running ...

If the login fails, you will see an error message in the console output:

 ERROR RealTimeController - Login failed: Unauthorized: check credentials!
 ERROR RealTimeRunner - Bad credentials - cannot run RealTimeService without valid admin/host
 INFO  RealTimeRunner - Initiating graceful shutdown of RealTimeService...

The output depends on the users and devices that are configured for the admin. +
In this case the admin has no devices and users configured.

=== Realtime *Context*

When building custom scenarios or running external applications, code often executes outside of a Spring application container—for example, in plain Java classes instantiated via a standard `new Scenario()` call. In those situations, Spring dependency injection (`@Autowired`) is not available, and attempting to inject beans directly causes a `NullPointerException`.

At the same time, driving a real-time scenario demands access to multiple cooperating subsystems:

* REST API (`Api`)
* Realtime Controller (`RealTimeController`)
* Tracker Registration (`TrackerRegistration`)
* Realtime Service (`RealTimeService`)
* Admin Session (`getRealtimeAdmin()`)

The `RealTimeContext` resolves this by serving as a unified facade and single injection point. 
Instead of passing around individual components or wiring Spring contexts into external modules, 
callers receive one cohesive context (typically via a `setContext(RealTimeContext)` hook). 
This gives scenarios the freedom to either leverage the high-level convenience methods of `RealTimeService` 
or drill down into fine-grained low-level APIs whenever custom behavior is needed.


=== Realtime *Runner*

By running the `jar` file or running Integration Tests, +
we have two entry points to start the Realtime Service. 

[source,text]
----
	Spring Boot Startup
	    └─→ RealTimeRunner (entry point)
	         ├─→ initialize RealTimeService
	         └─→ login via Api
----

You should find log entries of `RealTimeRunner.run(..)` in the console output:
