== `GpsPlayerIT`

Just like the `TrackerOsmAnd` has the `GpsTrackerIT` to test the tracker in action, +
the `PlayerOsmAnd` has the `GpsPlayerIT` to develop and test the player in action. +
As described earlier, we have two main test methods to cover the basic use cases of the player:

[source,java]
----
  @Test     // single track, single tracker
  void loadSingleGpxAndSendWithSingleTracker() throws Exception {

  @Test     // multiple tracks, multiple trackers
  void loadFourGpxAndSendWithFourTrackers() throws Exception {
----

Let's look at the player test as a step by step implementation 
for your real world application.


=== create a Player

If you already have a tracker instance you can use it with the player to play the track. 

[source,java]
----
    PlayerOsmAnd player = new PlayerOsmAnd();
    player.setTracker(tracker);
    player.load(gpxFile);
----


=== play the track

To play the track, we simply call 

[source,java]
----
    player.playOsmAndTrack()).isTrue();
----

to start the scheduling of messages based on their _timestamp differences_. +
The method validates the tracker, the message list and the index in the list.
Due to different starting conditions of various players the startup procedure
can run into race conditions. 
The method

[source,java]
----
    player.ensurePlaybackRoutes();
----

is setting up the scheduler and the scheduler bean in a safe manner
and adds the actual trigger route.
After the camel context has started the first message is triggered immediately, 
and delegates scheduling of all subsequent messages to the `QuartzSchedulerBean`.


=== `QuartzSchedulerBean`

When starting the playback the first message is triggered 

[source,java]
----
    quartzScheduler.sendCurrentAndScheduleNext();
----

and the scheduler does his work by sending a message +
and instantly scheduling the delay to the next message - again - and again.

[source,java]
----
    player.tracker.sendMessage(current);
     :
    scheduleFireIn(delayMs);
----

The actual rescheduling is done directly on the `Scheduler` using the native Quartz API 
— no Camel producer endpoint involved here.

[source,java]
----
    quartzScheduler.rescheduleJob(triggerKey, newTrigger);
----

== Graceful Shutdown

=== problem: Teardown Race Conditions

When running multiple players in a scenario (e.g., `ScenarioIT`), 
a race condition can occur during scenario teardown:

1. A scenario completes and logs "scenario completed"
2. Pending Quartz triggers continue to fire in background threads
3. During broader context teardown, tracker routes are being removed
4. Late playback callbacks attempt to send messages to routes that no longer exist
5. This results in errors like `SedaConsumerNotAvailableException: No queue available on endpoint`

This is especially problematic in long-running scenarios where messages are spaced far apart 
(e.g., 2+ minutes between GPX points), because the final messages may still be scheduled 
when the scenario teardown begins.

=== solution: stopOsmAndTrack()

The `PlayerOsmAnd` class now provides a graceful shutdown API:

[source,java]
----
public synchronized void stopOsmAndTrack() {
    stopRequested = true;
    
    if (camel == null) {
      return;
    }

    try {
      camel.stop();
    } catch (Exception e) {
      logger.warn("Failed to stop playback Camel context cleanly.", e);
    } finally {
      camel = null;
      quartzScheduler = null;
    }
  }
----

When `stopOsmAndTrack()` is called:

1. A `stopRequested` flag is set to `true`
2. The per-player Camel context is stopped gracefully
3. References to the context and scheduler are cleared

Additionally, a synchronized getter exposes the stop state:

[source,java]
----
synchronized boolean isStopRequested() {
    return stopRequested;
}
----

=== Stop Flag Integration

The `QuartzSchedulerBean` checks the stop flag before scheduling and sending:

[source,java]
----
// In scheduleFireIn()
if (player.isStopRequested()) {
  return;
}

// In sendCurrentAndScheduleNext()
if (player.isStopRequested()
    || player.tracker == null
    || player.osmandTrack == null
    || ...) {
  return;
}
----

This ensures that any pending Quartz callbacks simply no-op instead of trying to 
send messages to routes that have been torn down.

The `playOsmAndTrack()` method also resets the stop flag when restarting, 
allowing players to be reused:

[source,java]
----
public synchronized boolean playOsmAndTrack() {
    if (tracker == null || osmandTrack == null || osmandTrack.isEmpty()) {
      return false;
    }
    if (nextIndex >= osmandTrack.size()) {
      return true;
    }

    stopRequested = false;  // <-- Reset on restart
    
    if (!ensurePlaybackRoutes()) {
      return false;
    }
    // ...
}
----

=== Test Integration

In scenarios like `ScenarioIT`, an `@AfterEach` teardown method 
stops all players gracefully before the broader context shutdown:

[source,java]
----
@AfterEach
void stopAllPlayers() {
  if (allPlayers == null || allPlayers.isEmpty()) {
    return;
  }

  logger.info("\t********** Stopping all GPS players gracefully **********");
  for (PlayerOsmAnd player : allPlayers) {
    player.stopOsmAndTrack();
    logger.info("Stopped playback for tracker: {}", 
                player.getTracker().getUniqueId());
  }
}
----

This ensures that by the time the scenario framework tears down tracker routes and contexts, 
all scheduled playback callbacks have already been silenced by the stop flag. +
This cleanly prevents `SedaConsumerNotAvailableException` and other endpoint-not-found errors 
that would otherwise pollute the logs and potentially cause unexpected failures.
