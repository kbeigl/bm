= The GPS Player

We have prototyped the first `gps-*-tracker` as a `@Component` that we can 'attach' to any thing. +
Next we will create a helper for further tracking developments,
which has proven to be very helpful during 
https://github.com/kbeigl/jeets/tree/master/jeets-clients/jeets-player[JeeTS]
development.
With a player software you can choose of thousands of available tracks and replay them. 
Beyond that a number of simulations can be used to replay complex traffic situations.

In the left image you can see the trackpoints of the track, which are (artifically!) connected by straight lines. 
The motorcycle is driving from top to bottom, i.e. from north to south.
In this special case the GPS signals are also distorted by hills and dense forests. +
It is obvious that the track cannot serve as a realistic track for a Driver Assistence System. +
For a Navigation System it is not a problem, since it does not actually steer the vehicle, 
but only provides instructions for the next maneuver. 
We do need the road network with a certain precision to snap the track points to the road network.
In the middle image you can see the track with arrows and a small "rounding" algorithm applied to the track points.

Another way to visualize the track is using OpenStreetMap Tools - the image on the right.
If we have a look at the curves of the track shown above, 
we can see a high precision of track points, which are actually in the middle of the road.
This is not only a result of numerous track points, but the roads are actually modeled
against various real world data sources. 

Note that the Map projection is different in the right image, which is helpful for editing.

In the following image you can see four tracks with trackpoints in different colors +
recorded on the same route in different directions:

image::RGB-BUELL-NE.png[RGB-BUELL-NE Track]
// image::RGB-BUELL-NE-arrows.png[RGB-BUELL-NE Track with Arrows]

Obviously the playback of all four tracks would be a nightmare for a Driver Assistence System. 
Programmed collisions and wrong speed and acceleration values would be the result of the distorted GPS signals.
Nevertheless all trackpoints together roughly outline the real road and 
we can tell the different driving sides of the road in different directions.

Since the ROAF is all about realistic simulations we could use the road data for guidance.
Be aware that road data only describes the geometry of the road, but does not contain any information about the traffic, weather, grip.
And it does not contain vehicle information to actually drive the vehicle.
And another challenging aspect is the over the air (OTA) transfer of many track points,
which does not always allow real-time processing.

For the time being we can agree on the constraint

=== Track Recording

As described in the
xref:../../bm-traccar/traccar-realtime-client/integrated-dev-cycle.adoc#_integrated_tracker_development[Integrated Tracker Development]
we still need to create features for the `gps-tracker`:

- [ ] time / distance intervals
- [ ] angular change (course over ground)
- [ ] motion start/stop

These features are actually related to the _recording_ of the track, which is a crucial aspect for the realism of the track.
Trackers can be configured to record tracks with different settings, 
which can lead to very different track qualities. 
Trackers for different purposes and with different hardware and software components can produce very different tracks. 
The highest precision of track recording is achieved with a high recording frequency and additional sources like a
Differential GPS (DGPS) or a Real Time Kinematic (RTK) GPS, which can provide centimeter-level accuracy. 

_We will *not* implement these features in the GPS Playback development environment_  `GpsTrackerIT` ! 

The reason becomes apparent when we look at the track points in the images above.
Just imagine we would apply time / distance intervals and / or angular changes.
There would be a massive regression in the track quality 
and the track would be even less realistic than it already is.

Vice versa, if you record a track with your vehicle you should apply small angular changes 
to trigger the recording exactly at the turning points. 
This way the recorded track polyline becomes more realistic 
and the route length comes closer to the real curvy route length.


== Player Components

The `gps-osmand-tracker` component is designed to be fed with position updates. +
The `gps-osmand-player` is a software that can read position updates from 'sources', + 
tranform them into the format `MessageOsmand` and feed them into one or more `gps-osmand-tracker`.

[mermaid, source-player-tracker, title="Components of the GPS Player: Parser, Timer and Tracker"]

  T1 -->|publish positions| TRACCAR
  TN -->|publish positions| TRACCAR
....

The figure above is actually a scrible of or a first approach to the `gps-osmand-player` architecture. 
On a closer look at the three main components: the `gpx-parser`, the `gps-timer` and the `gps-tracker`,
we can subdivide the components into loading and parsing from any source into `MessageOsmand` 
and then scheduling the position updates to the trackers.

The interface between loading and playing is the `List<MessageOsmand>`. +
The player can be applied in any environment that can provide this list. +
To differentiate between the two parts we are testing the player against the `bm` framework. +
And we will provide a `gpx-player.jar` to run the player as a standalone application.

To separate the loading, generally the ETL part and the playing of the track,
we use the `gpx-` and `gps-` prefixes to distinguish the two parts of the player software,
which is also reflected in the package names `bm.gps.gpx` and `bm.gps.player` 
Helpful for aspect oriented programming (AOP) approaches.

The loader and parser form the ETL part of the player, 
which is responsible for loading and parsing the track data from any source.

== Geo Helpers

As the framework grows the supporting libraries and helper classes grow as well.
During player development we faced the new constellation of two consecutive track points 
and the need to calculate speed and bearing between them. 

This has brought up the TrackPoint record in our `GeoTools` class and + 
the following helper methods to calculate speed and bearing between two track points:

[source,java]
----
         speedMetersPerSecond(TrackPoint previous, TrackPoint current)
     normalizedBearingDegrees(TrackPoint previous, TrackPoint current)
     private helper normalizeBearing(double bearing)
----

The `GpxToMessageOsmandParser` was updated to use 

[source,java]
----
    speed   = GeoTools.speedMetersPerSecond(previous, point);
    bearing = GeoTools.normalizedBearingDegrees(previous, point);
----

we'll take care of the units `[m/s]` to `[km/h]` to `[mph]` etc. , when we get there.


== Outlook

The main idea of a `gps-player` is to re/play the GPS track of a single device +
by feeding each position update into a `gps-tracker` component.

The real/istic GPS Track can be recorded with a real GPS device,
tranformed into any file format with any GIS, OpenStreetMap or geo software in general - even online.
Besides using files we can also access a database (like on the Traccar server) to extract position updates.


=== real world traces

GPS traces are more than just a list of positions at certain times.
If they are recorded with a real vehicle with a hardware GPS device
they actually contain a lot more information about the environment and the vehicle itself. 

Motorcycle race tracks are a good example.
The team analyzes the GPS traces of the motorcycle to optimize the performance of the bike and the rider
- against the track and down to track segments - on that very day with given grip, weather and so on.

The ROAF has one very central constraint: everything is live! +
In order to actually simulate a `RealVehicle` we need to collect a lot of parameters as we drive.

On the other hand the `RealTimeController` should grow to a mature ROAF validator (see ROAF TT) against reality. +
In case of vehicles we are talking about classical physics of motion.


=== synthetic tracks

Of course we can also create synthetic tracks with a track editor or even generate them with a script.
The problem is the definition of the timestamps.
These actually _should_ describe the physics of the movement and are crucial for a realistic simulation.

The challenge of the ROAF will be to apply a `RealTimeController` to validate the real-time behavior of the system. 


=== map segments

A digital map describes a route in terms of links and edges, which is nothing but
a sequence of GPS Positions connected by straight lines.
A navigation system is able to extract a path from current location to a destination Position.
Yet this path or route does not provide timestamps and is purely spatial.


=== Player > Navigator > Driver

We can extract routes from a digital map and then tell our Device, or rather the vehicle carying it 
to follow this route with adopted speed. 
This way the `gps-player` can become a (proven) starting point for a Navigation System.

Once we will be able to navigate a Device, we can even go a step further: +
We can implement some self driving algorithms to create a `Driver`
and when we add environmental information from the `RealTimeController` 
we can create something like an ADAS, a Driver Assistence System.
