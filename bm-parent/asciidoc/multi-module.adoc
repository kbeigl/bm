= Multi Module Repository

This `bm-sim` repository is a 
link:https://maven.apache.org/guides/mini/guide-multiple-modules.html[Maven Multiple Module] 
project.
The Maven Reactor mechanism makes sure to collect all modules 
and assert correct build order with every `mvn` command executed. 
It assures that any project is build as required by another.

We use the Maven multi-module project approach for managing distributed applications 
where different components need to be developed, versioned, and deployed _independently_ 
while maintaining coherent dependencies centralized.
This simplifies and standardizes a consistent build process 
and scaling with a clear separation of concerns.

This is a Java project and the development cycle 
is defined by the major components:


== Maven build tool 
 
Implies `major.minor.patch` versioning (sometimes with -RC, -POC etc. to indicate the build status)
, dependency management, plugin configuration, 
build lifecycle and finally release management.
If available and feasible external tools, i.e. plugins, like the 
link:https://github.com/OpenAPITools/openapi-generator[OpenAPI Generator]
are integrated into the lifecycle to generate code for subsequent modules.


== Camel Integration Framework 

Apache Camel has a very powerful bean injection framework 
to allow developers _to focus on solving business problems_. 
At its core, Apache Camel is an integration engine, which can be used 
to facilitate 
interactions between a wide and varied array of technologies. 
These bridges between service- and technology _Endpoints_, 
the _Routes_ are implemented on an engine - the _CamelContext_,  
and they communicate with _Exchange Messages_.

In this repository Camel is used to glue independantly developed Units together.


== Camel & Spring

*Camel* allows you to define your data flow as a declarative route 
for complex integration and routing work,
and then handing off the final business logic
to standard *Spring* components like Controllers or Services.
While *Spring Boot* handles the lifecycle and dependency injection 
in the Spring context, dependency injection, and application startup.

[NOTE]
====
 Spring Boot will auto-configure Camel for you.
====
 
check out 
https://camel.apache.org/camel-spring-boot/spring-boot.html[camel-spring-boot]

Spring Boot component provides auto-configuration for Apache Camel. 
Our opinionated auto-configuration of the Camel context 
auto-detects Camel routes available in the Spring context 
and registers the key Camel utilities 
(like `producer` and `consumer` templates, type converters etc.) as `@Bean`.


== `@SpringBootApp` s

// and `@CamelSpringBootApplication`

We are building a multi-module project from multiple Spring projects. + 
Each project has its own technology stack and can be used independently
or as a part of the whole system.

The `@SpringBootApplication` annotation is a convenience annotation that adds all of the following: 

1. `@Configuration`: Tags the class as a source of bean definitions for the application context.
2. `@EnableAutoConfiguration`: Tells Spring Boot to start adding beans based on class
path settings, other beans, and various property settings.
3. `@ComponentScan`: Tells Spring to look for other components, configurations, and
services in the package, allowing it to find the controllers.

This is very useful for our multi-module project, 
as it allows us to define the main application class in one module 
and have it automatically discover and configure beans from other modules.


=== `bm` library as of `v.1.1.25`

On the other hand you run into design problems, if you have multiple `@SpringBootApplication` classes in your project,
If one `@SpringBootApplication` class is in a module that is not a dependency of the main application module, 
then Spring Boot will not be able to discover and configure beans from that module.

As the `traccar-realtime-client` module is a dependency of the `traccar-realtime-app` module,
a `@SpringBootApplication` class in the `traccar-realtime-client` module 
would be discovered and configured by Spring Boot when the `traccar-realtime-app` module is run.

**Why this is problematic:**

1. When `traccar-realtime-app` imports this as a library, it gets:
   - Duplicate component scanning (both apps scan `bm.traccar` package)
   - Potential bean conflicts
   - Unnecessary application context overhead
2. The `@SpringBootApplication` in a library forces component scanning on consumers
3. Cannot control which components are loaded when used as dependency

Therefore the mixed  pattern of the `@SpringBootApplication` annotation causing component scanning conflicts  
was removed from the `traccar-realtime-client` module in `v.1.1.25`.
All projects should be usable as library for higher level projects.

The standard pattern to separate @SpringBootApplication from libraries is:

Libraries should:

    •  Use @Configuration + @ComponentScan instead of @SpringBootApplication
    •  NOT have spring-boot-maven-plugin in pom.xml
    •  Provide explicit configuration classes that applications import
    •  Use @Component/@Service/@Repository for beans

Applications should:

    •  Have @SpringBootApplication
    •  Use @Import(LibraryConfig.class) to explicitly include library components
    •  Have spring-boot-maven-plugin configured with mainClass
    •  Control what gets scanned and loaded


==== Dual Purpose

The `gps-osmand-tracker` application module is a dual purpose module, 
which can be used as a standalone application or as a library for other applications.

*Pattern* +
Library with optional standalone application

*Structure*

[source,xml]
----
    src/main/java/bm/gps/tracker/
    ├── TrackerOsmandConfig.java          (@Configuration, @ComponentScan)
    ├── TrackerApplication.java           (@SpringBootApplication)
    ├── TrackerOsmand.java                (@Component)
    └── TrackerRegistration.java          (@Component)
----


*Separate Configuration*

[source,java]
----
    @Configuration
    @ComponentScan(basePackages = "bm.gps.tracker")
    public class TrackerOsmandConfig {
        // This config lives in main sources so other modules 
        // can import it without depending on the test-jar.
    }
----

*Standalone Application:*

[source,java]
----
    @SpringBootApplication
    public class TrackerApplication {
        public static void main(String[] args) {
            SpringApplication.run(TrackerApplication.class, args);
        }
    }
----

*Advantages*

    ✅ Library provides configuration
    ✅ Application can optionally use library components
    ✅ Can have both library and standalone app in same module


=== `@ComponentScan` and `@Import`

We have changed the `traccar-realtime-client` module to use `@Configuration` and `@ComponentScan` + 
instead of `@SpringBootApplication`:

[source,java]
----
    @Configuration
    @ComponentScan(basePackages = {"bm.traccar", "bm.traccar.rt", "bm.traccar.ws"})
    @Import({ApiConfig.class, ScenarioConfig.class}) // Import dependency configs
    public class RealTimeConfig {}
----

Generally you can create your own @SpringBootApplication class in your application module + 
and import the library configuration classes as needed.

[source,java]
----
    @SpringBootApplication
    @Import(RealTimeConfig.class)  // Import library configuration listed above
    public class MyApplication {
        
        public static void main(String[] args) {
            SpringApplication.run(MyApplication.class, args);
        }
    }
----
